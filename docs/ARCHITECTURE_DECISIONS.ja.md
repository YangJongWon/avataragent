## ADR-001: 現在のオーケストレーターを維持し、LangGraph は実行器の選択肢として残す

状態：ADR-003 により置き換え  
決定日：2026-10-04

### 決定

現在の TypeScript オーケストレーターを主な実行器として維持する。UI の業務の旅は、特定のフレームワーク形式ではなくアプリ共通の Workflow モデルとして保存する。LangGraph が必要になったら、Workflow 実行器インターフェースの背後に別のアダプターとして追加する。

### いま LangGraph を導入する場合の利点

- チェックポイントと中断・再開の概念がすでに整理されている。
- ユーザー承認のように長く止まる human-in-the-loop のフローを実装しやすい。
- 条件分岐、並列実行、サブグラフが複雑になるほど自前の実装量が減る。
- 実行トレースのエコシステムとサンプルが豊富である。
- 長時間実行のワークフローをチームが共通の方法で理解しやすい。

### 欠点

- 現在の逐次実行、レビューでの差し戻し、ヘルプ要請、承認のフローはすでに自前のコードで動いているため、重複実装になる。
- フレームワークの状態とアプリ DB の状態が二重化し、どちらが正なのか曖昧になりうる。
- ピクセルアニメーション用の細かなイベントを LangGraph の実行イベントに再マッピングする必要がある。
- デバッグ箇所とデプロイ構成要素が増える。
- フレームワーク API の変化と特定のエコシステムへの依存が生じる。

### 導入を再検討する条件

以下の条件のうち 2 つ以上が実際の要件として生じたら、LangGraph アダプターを検討する。

- 独立したステップの並列実行と合流が多くの業務で必要になる。
- 1 つの業務が数日続き、外部シグナルを繰り返し待つ。
- 入れ子のサブワークフローと動的分岐が一般的になる。
- 自前の再開・補償ロジックの維持費が実行器アダプターの維持費を上回る。
- LangGraph ベースの外部ワークフローを取り込んだり書き出したりする必要がある。

### 現在の実装原則

- UI とストレージはアプリ共通の Workflow モデルだけを知る。
- モデル呼び出し、ツール実行、承認状態は明示的なステップイベントとして記録する。
- 実行器はチェックポイント以降から冪等に再開できなければならない。
- LangGraph を追加してもオフィス UI とレポートのデータモデルは変更しない。

## ADR-003: Temporal を永続実行レイヤーとして採用する

状態：採用  
決定日：2026-10-04

### 背景

製品は特定のエージェントフレームワークよりも汎用性と長期的な保守のしやすさを優先する。業務は数秒から数日まで続くことがあり、ユーザー承認、予約、外部イベント、リトライ、並列処理、交代実行が必要になる。これらの責務をアプリ自前のコードで実装し続けると、復旧・バージョン互換・冪等性のコードが製品ロジックより大きくなる可能性が高い。

### 決定

Temporal を業務の永続実行レイヤーとして採用する。アプリの Workflow Spec は Temporal から独立して維持し、コンパイラーがそれを Temporal の Workflow と Activity 呼び出しに変換する。

```text
オフィス UI / フローチャート
        ↓
中立的な Workflow Spec
        ↓
WorkflowRuntime インターフェース
        ├─ TemporalRuntime（本番の既定）
        └─ LocalRuntime（開発・移行）
                ↓
AgentRuntime インターフェース
        ├─ モデル API 直接
        ├─ LangGraph
        └─ その他のエージェント SDK
                ↓
ToolRuntime / MCP
```

### Temporal を選んだ理由

- プロセスやサーバーの障害後、イベント履歴から実行を復元する。
- ユーザー承認や外部シグナルを、プロセスを占有せずに長く待てる。
- Activity 単位のタイムアウト、リトライ、キャンセル、タスクキューを提供する。
- 予約業務、交代勤務、並列実行、サブワークフローを通常の業務機能として扱える。
- モデル提供会社とエージェントフレームワークから独立している。
- セルフホストとマネージド Cloud から選べる。

### コストと欠点

- Temporal Service と Worker を運用するか、Cloud の費用を負担する必要がある。
- Workflow コードは決定的でなければならず、LLM・DB・ネットワーク呼び出しは Activity に分離する必要がある。
- 実行中の Workflow と新しいコードの互換性を管理する必要がある。
- ローカルのプロトタイプでは、既存の実行器より構成と学習のコストが大きい。

### LangGraph の位置づけ

LangGraph は製品全体の運用エンジンではなく、1 つの Activity の中で複雑なエージェントグラフが必要なときに使う選択的な AgentRuntime である。単純な調査・作成・レビューはモデル直接アダプターを使い、動的分岐やサブエージェントの探索が必要な業務だけ LangGraph を選ぶ。

### 移行の原則

- API と UI は Temporal SDK を直接呼び出さない。
- PostgreSQL は製品データの基準ストレージであり、Temporal は実行履歴の基準ストレージである。
- レポートや大きな成果物は PostgreSQL またはオブジェクトストレージに保管し、Workflow History には ID だけを置く。
- 外部に書き込むすべての Activity は安定した冪等キーを使う。
- 既存の LocalRuntime は移行期間と単一 PC の開発モードでのみ維持する。

## ADR-002: リレーショナルな永続化とストレージ境界

状態：進行中  
決定日：2026-10-04

### 決定

単一の `kv.state` JSON 保存をリレーショナルなコレクションテーブルに移行する。当初はデプロイが簡単な SQLite を維持しつつ、スキーマのマイグレーションとトランザクションを導入し、PostgreSQL に移せるストレージ境界を作る。

### ステップ

1. SQLite のリレーショナルテーブルと自動マイグレーション
2. 既存の `kv.state` の自動インポート
3. 業務実行のチェックポイントと呼び出し台帳の追加
4. ストレージインターフェースの分離
5. PostgreSQL の実装と本番環境の切り替え

### 本番環境の最終要件

- PostgreSQL のマネージドインスタンス
- 組織・ユーザー・プロジェクトごとのテナント ID と行レベルの分離
- 暗号化されたシークレットの保存
- 定期バックアップとポイントインタイムリカバリー
- マイグレーションのロールバック手順
- コネクションプール、読み書きのタイムアウト、障害アラート
- 監査ログの保存ポリシー
- 個人情報の削除と保存期間のポリシー

## ADR-004: プロジェクトサイトとライセンスキーでプランを販売する

状態：進行中（ステップ 5 まで完了）  
決定日：2026-10-05

### 背景

アプリは会社ごとに自分の PC やサーバーにインストールして使う。そのため、中央で決済してもお客様のアプリのプランは自動的には変わらない。同時に、テーマ・フロー・プレイブックを共有するコミュニティと、チーム・ビジネスプランの販売窓口が必要である。

### 決定

- 同じリポジトリの `site/` に公開サイトを置く。スタックはアプリと同じ（TypeScript・React・Express・PostgreSQL）で、フォーマット検証などの共通コードは `shared/` を共用する。本番は PostgreSQL（Neon など）、開発とテストは組み込みの PGlite で同じ SQL を使う。
- ログインはメールのマジックリンク・Google・GitHub で、検証済みのメールアドレスで 1 つのアカウントにまとめる。
- プランは **署名されたライセンスキー** で販売する。サイトが Ed25519 で署名したトークンを発行し、アプリは公開鍵で検証する。アプリがサイトに問い合わせる方向（プル）だけを使い、公開アドレスのないインストールでも動作するようにする。アプリ側は既存の `BillingProvider` 構造に `site` プロバイダーを加え、更新は `billingTick`、延滞の猶予は既存の `GRACE_DAYS` をそのまま使う。
- 決済会社はアダプターの背後に置き、実際の連携（Toss Payments・Paddle など）は後で選ぶ。それまでは mock 決済で全体のフローを完成させる。
- コミュニティは、テーマ・フロー・プレイブックのギャラリー、クリエイタープロフィール・ランキング、掲示板・Q&A、有料テーマ販売の順に段階的に開く。

### サイトに届かないとき

アプリは決済期間が終わる 3 日前から 6 時間ごとにサイトに新しいライセンスを問い合わせる。期間が過ぎてもサイトに届かなければ決済失敗として扱い、既存の 7 日間の猶予が過ぎると個人プランに戻る。サイトがライセンスを拒否した場合（別のインストールに移された、または削除された）は、すぐにサブスクリプションを終了する。

### コミュニティの項目

- 検証コードはアプリとサイトで同じものを使う（`server/theme-package.ts`、`shared/flow-pack.ts`、`shared/playbook.ts`）。サイトは検査を通過して整理されたファイルだけをバージョンごとに保存し、バージョンは変更しない。
- 業務フローには担当スタッフの代わりに役割だけを入れる。受け取る側のオフィスで同じ役割のスタッフ（いなければ最初のスタッフ）に割り当て、ルール検査はアプリの `validatePlan` をそのまま使う。
- アプリのワンクリックインストールでは、アプリサーバーが `SITE_URL` からのみ、形式の正しい項目 id でのみダウンロードする（SSRF 防止）。テーマのインストールとフローの保存はオフィスのオーナーだけが行う。

### 運用

- ランキングは保存せず、ダウンロードの日別集計といいねの時刻からその都度計算する（いいね 1 = ダウンロード 3）。規模が大きくなったら日別スナップショットテーブルに移す。
- 3 人から通報されると自動で非表示にする。通報で非表示になったものは作成者が再公開できず、運営者だけが元に戻せる。運営者の操作はすべて `audit_log` に残す。
- 停止はアカウントの状態 1 つで扱い、セッションを削除する。停止されたアカウントの項目と投稿は自動では削除せず、キューから 1 件ずつ処理する。

### 有料テーマ

- 販売はプランと同じ決済アダプターと決済イベント処理（重複イベントは無視）を使う。購入 1 件は `purchases` の 1 行で、購入した人だけがダウンロードできる。
- お金の流れは変更しない台帳（`ledger`）に符号付きの金額としてだけ残す。残高は合計で計算し、別途保存しない。クリエイター 70% / 運営 30%。
- 支払いは決済会社の精算機能を選ぶまで、運営者が直接送金して記録する。支払い記録は残高を超えないよう、アカウント行をロックして確認する。
- アプリのワンクリックインストールは無料の項目だけを対象とする。有料テーマはサイトで購入し、受け取った zip をアプリに入れる（機器ログイン連携は今後）。

### 決済会社：Paddle

- 海外（4 言語）での販売のため、販売代行（merchant of record）である Paddle を選ぶ。国ごとの付加価値税と領収書は Paddle が担当し、韓国の販売者も登録できる（Stripe は韓国の販売者を受け付けていない）。
- 決済結果は署名された Webhook でのみ反映し、ブラウザーはその反映を待ってから戻る。更新は Paddle が請求・通知するため、サイトの時計では更新しない。
- 有料テーマ（他のクリエイターによる販売）が Paddle のポリシーに合うかは実アカウントの申請時に確認し、合わなければ有料テーマだけ別の決済経路に回す。

### ライセンスを強く制限しない理由

アプリは AGPL なので、誰でも検証コードを変更できる。ライセンスキーは誠実なユーザーが決済をすぐに適用・更新できるよう手助けする仕組みとし、コピー防止（DRM）は行わない。商用の再配布は商用ライセンスで扱う。

### ステップ

1. サイトの骨格：DB・マイグレーション、3 種類のログイン、紹介・料金・インストール・ドキュメント（完了）
2. ライセンスとプラン販売：署名キー、mock 決済、発行・更新・移転、アプリの `site` 決済プロバイダーとプラン画面（完了）
3. コミュニティギャラリーとアプリ連携（コミュニティタブ、ワンクリックインストール）、フロー共有フォーマット `avataragent-flow`（完了）
4. クリエイタープロフィール・ランキング、掲示板・Q&A、審査（完了）
5. 有料テーマ販売と精算台帳（完了）
6. 実際の決済会社との連携とクラウドデプロイ — Paddle アダプター完了（サンドボックスでのテスト・デプロイ・実アカウントの審査が残り）
