## ADR-001：保留现有编排器，将 LangGraph 作为执行器选项

状态：已被 ADR-003 取代  
决定日期：2026-10-04

### 决定

保留现有的 TypeScript 编排器作为主执行器。界面中的工作流以应用通用的 Workflow 模型保存，而不是某个特定框架的格式。如果需要 LangGraph，再将其作为独立适配器添加到 Workflow 执行器接口之后。

### 现在引入 LangGraph 的优点

- 检查点以及暂停、恢复的概念已经很成熟。
- 便于实现像用户批准这样需要长时间暂停的 human-in-the-loop 流程。
- 条件分支、并行执行和子图越复杂，需要自行实现的量就越少。
- 执行追踪生态和示例丰富。
- 团队容易用统一的方式理解长时间运行的工作流。

### 缺点

- 现有的顺序执行、审核驳回、求助和批准流程已经由自有代码实现，会造成重复实现。
- 框架状态和应用数据库状态会出现双份，可能分不清以哪一方为准。
- 用于像素动画的细粒度事件需要重新映射到 LangGraph 的执行事件上。
- 调试点和部署组件会增加。
- 会依赖框架 API 的变化和特定生态。

### 重新考虑引入的条件

当下列条件中有两个以上成为实际需求时，再考虑 LangGraph 适配器。

- 多个任务需要独立步骤的并行执行与汇合。
- 单个任务持续多天，并反复等待外部信号。
- 嵌套子工作流和动态分支变得普遍。
- 自有恢复、补偿逻辑的维护成本超过执行器适配器的维护成本。
- 需要导入或导出基于 LangGraph 的外部工作流。

### 当前实现原则

- 界面和存储只认应用通用的 Workflow 模型。
- 模型调用、工具执行和批准状态以明确的步骤事件记录。
- 执行器必须能够从检查点之后幂等地恢复。
- 即使添加 LangGraph，办公室界面和报告数据模型也不改变。

## ADR-003：采用 Temporal 作为持久化执行层

状态：已采用  
决定日期：2026-10-04

### 背景

产品优先考虑通用性和长期维护的便利性，而不是某个特定的智能体框架。任务可能持续几秒到几天，需要用户批准、定时、外部事件、重试、并行处理和轮班执行。如果继续用应用自有代码实现这些职责，恢复、版本兼容和幂等相关的代码很可能比产品逻辑还多。

### 决定

采用 Temporal 作为任务的持久化执行层。应用的 Workflow Spec 保持独立于 Temporal，由编译器将其转换为 Temporal Workflow 和 Activity 调用。

```text
办公室界面 / 流程图
        ↓
中立的 Workflow Spec
        ↓
WorkflowRuntime 接口
        ├─ TemporalRuntime（生产默认）
        └─ LocalRuntime（开发、迁移）
                ↓
AgentRuntime 接口
        ├─ 直接调用模型 API
        ├─ LangGraph
        └─ 其他智能体 SDK
                ↓
ToolRuntime / MCP
```

### 选择 Temporal 的原因

- 进程或服务器故障后，可以从事件历史中恢复执行。
- 可以长时间等待用户批准和外部信号，而不占用进程。
- 提供以 Activity 为单位的超时、重试、取消和任务队列。
- 可以把定时任务、轮班、并行执行和子工作流当作普通任务功能来处理。
- 独立于模型提供商和智能体框架。
- 可以在自托管和托管 Cloud 之间选择。

### 成本与缺点

- 需要运维 Temporal Service 和 Worker，或承担 Cloud 费用。
- Workflow 代码必须是确定性的，LLM、数据库和网络调用必须拆分到 Activity 中。
- 需要管理正在运行的 Workflow 与新代码之间的兼容性。
- 对本地原型而言，配置和学习成本比现有执行器更高。

### LangGraph 的定位

LangGraph 不是整个产品的运行引擎，而是在单个 Activity 内需要复杂智能体图时使用的可选 AgentRuntime。简单的调研、撰写和审核使用直接模型适配器，只有需要动态分支或子智能体探索的任务才选用 LangGraph。

### 迁移原则

- API 和界面不直接调用 Temporal SDK。
- PostgreSQL 是产品数据的权威存储，Temporal 是执行历史的权威存储。
- 报告和大型产出物存放在 PostgreSQL 或对象存储中，Workflow History 中只保存 ID。
- 所有对外写入的 Activity 都使用稳定的幂等键。
- 现有的 LocalRuntime 只在迁移期间和单机开发模式下保留。

## ADR-002：关系型持久化与存储边界

状态：进行中  
决定日期：2026-10-04

### 决定

将单一的 `kv.state` JSON 存储迁移到关系型集合表。初期继续使用部署简单的 SQLite，但引入模式迁移和事务，并建立可以迁移到 PostgreSQL 的存储边界。

### 步骤

1. SQLite 关系型表和自动迁移
2. 自动导入现有的 `kv.state`
3. 添加任务执行检查点和调用账本
4. 拆分存储接口
5. PostgreSQL 实现和生产环境切换

### 生产环境的最终要求

- 托管的 PostgreSQL 实例
- 按组织、用户和项目划分的租户 ID 与行级隔离
- 加密存储密钥
- 定期备份和时间点恢复
- 迁移回滚流程
- 连接池、读写超时和故障告警
- 审计日志保留策略
- 个人信息删除及保留期限策略

## ADR-004：通过项目网站和许可证密钥销售套餐

状态：进行中（已完成至第 5 步）  
决定日期：2026-10-05

### 背景

每家公司都把应用安装在自己的电脑或服务器上使用。因此，即使在中心完成付款，客户应用的套餐也不会自动改变。同时，还需要一个分享主题、流程和剧本的社区，以及销售团队版和商业版套餐的渠道。

### 决定

- 在同一仓库的 `site/` 中放置公开网站。技术栈与应用相同（TypeScript、React、Express、PostgreSQL），格式校验等公共代码共用 `shared/`。生产环境使用 PostgreSQL（Neon 等），开发和测试使用内置的 PGlite，SQL 相同。
- 登录方式为邮箱魔法链接、Google 和 GitHub，并通过已验证的邮箱地址归并到一个账号。
- 套餐以 **签名的许可证密钥** 销售。网站签发用 Ed25519 签名的令牌，应用用公钥验证。只采用应用向网站查询的方向（拉取），这样没有公网地址的安装也能工作。应用端在现有的 `BillingProvider` 结构中增加 `site` 提供方，续期使用 `billingTick`，逾期宽限沿用现有的 `GRACE_DAYS`。
- 支付服务商放在适配器之后，真实对接（Toss Payments、Paddle 等）以后再选。在此之前用 mock 支付完成整个流程。
- 社区分阶段开放：主题、流程和剧本画廊，创作者主页和排行榜，论坛和问答，付费主题销售。

### 无法连接网站时

应用会在计费周期结束前 3 天开始，每 6 小时向网站请求新的许可证。如果到期仍无法连接网站，则按付款失败处理，在现有的 7 天宽限期过后回到个人版套餐。如果网站拒绝该许可证（已转移到其他安装或已删除），会立即终止订阅。

### 社区内容

- 应用和网站使用相同的校验代码（`server/theme-package.ts`、`shared/flow-pack.ts`、`shared/playbook.ts`）。网站只按版本保存通过检查并整理过的文件，版本不会被修改。
- 工作流只包含角色，不包含负责员工。在接收方的办公室中匹配到相同角色的员工（没有则为第一位员工），规则检查直接使用应用的 `validatePlan`。
- 应用的一键安装由应用服务器仅从 `SITE_URL`、仅按格式正确的条目 id 下载（防止 SSRF）。只有办公室所有者可以安装主题和保存流程。

### 运营

- 排行榜不保存，而是根据每日下载统计和点赞时间即时计算（1 个赞 = 3 次下载）。规模变大后再迁移到每日快照表。
- 被 3 人举报会自动隐藏。因举报而隐藏的内容，作者不能重新公开，只有运营者可以恢复。运营者的所有操作都记录在 `audit_log` 中。
- 封禁通过单一的账号状态处理，并清除会话。被封禁账号的内容和帖子不会自动删除，而是在队列中逐一处理。

### 付费主题

- 销售使用与套餐相同的支付适配器和支付事件处理（忽略重复事件）。一次购买对应 `purchases` 中的一行，只有购买者可以下载。
- 资金流动只以带符号的金额记录在不可修改的账本（`ledger`）中。余额按合计计算，不单独保存。创作者 70% / 运营方 30%。
- 在选定支付服务商的结算功能之前，由运营者手动转账并记录。付款记录会锁定账号行，确认不超过余额。
- 应用的一键安装只适用于免费内容。付费主题在网站购买后，把收到的 zip 放入应用（设备登录联动后续再做）。

### 支付服务商：Paddle

- 为了面向海外（4 种语言）销售，选择作为销售代理（merchant of record）的 Paddle。各国的增值税和收据由 Paddle 负责，韩国卖家也可以注册（Stripe 不接受韩国卖家）。
- 支付结果只通过签名的 Webhook 生效，浏览器会等到生效后再返回。续期由 Paddle 扣费并通知，因此不由网站的时钟驱动续期。
- 付费主题（其他创作者销售）是否符合 Paddle 的政策，会在申请正式账号时确认；如果不符合，只把付费主题转到其他支付渠道。

### 为什么不严格限制许可证

应用采用 AGPL，任何人都可以修改校验代码。许可证密钥只是帮助诚实用户立即应用和续期付款的机制，不做复制保护（DRM）。商业再分发由商业许可处理。

### 步骤

1. 网站骨架：数据库与迁移、3 种登录方式、介绍、价格、安装和文档页面（已完成）
2. 许可证和套餐销售：签名密钥、mock 支付、签发、续期和转移，应用的 `site` 计费提供方和套餐界面（已完成）
3. 社区画廊与应用联动（社区标签、一键安装），流程分享格式 `avataragent-flow`（已完成）
4. 创作者主页和排行榜、论坛和问答、审核（已完成）
5. 付费主题销售和结算账本（已完成）
6. 真实支付服务商对接和云端部署 —— Paddle 适配器已完成（还剩沙箱测试、部署和正式账号审核）
