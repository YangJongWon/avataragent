# 아키텍처 결정 기록

## ADR-001: 현재 오케스트레이터를 유지하고 LangGraph는 실행기 선택지로 둔다

상태: ADR-003에 의해 대체됨  
결정일: 2026-10-04

### 결정

현재 TypeScript 오케스트레이터를 주 실행기로 유지한다. UI의 업무 여정은 특정 프레임워크 형식이 아닌 앱의 공통 Workflow 모델로 저장한다. LangGraph가 필요해지면 Workflow 실행기 인터페이스 뒤에 별도 어댑터로 추가한다.

### LangGraph를 지금 도입할 때의 장점

- 체크포인트와 중단·재개 개념이 이미 정리되어 있다.
- 사용자 승인처럼 오래 멈추는 human-in-the-loop 흐름을 구현하기 좋다.
- 조건 분기, 병렬 실행과 하위 그래프가 복잡해질수록 직접 구현량이 줄어든다.
- 실행 추적 생태계와 예제가 풍부하다.
- 장기 실행 워크플로를 팀이 공통 방식으로 이해하기 쉽다.

### 단점

- 현재 순차 실행, 검수 반려, 도움 요청과 승인 흐름이 이미 자체 코드로 동작하므로 중복 구현이 된다.
- 프레임워크 상태와 앱 DB 상태가 이중화되어 어느 쪽이 진실인지 모호해질 수 있다.
- 픽셀 애니메이션용 세밀한 이벤트를 LangGraph 실행 이벤트에 다시 매핑해야 한다.
- 디버깅 지점과 배포 구성요소가 늘어난다.
- 프레임워크 API 변화와 특정 생태계에 대한 종속성이 생긴다.

### 도입을 다시 검토할 조건

아래 조건 중 둘 이상이 실제 요구로 발생하면 LangGraph 어댑터를 검토한다.

- 독립 단계의 병렬 실행과 합류가 여러 업무에서 필요하다.
- 하나의 업무가 여러 날 지속되고 외부 신호를 반복해서 기다린다.
- 중첩된 하위 워크플로와 동적 분기가 일반화된다.
- 자체 재개·보상 로직의 유지비가 실행기 어댑터 유지비보다 커진다.
- LangGraph 기반 외부 워크플로를 가져오거나 내보내야 한다.

### 현재 구현 원칙

- UI와 저장소는 앱의 공통 Workflow 모델만 안다.
- 모델 호출, 도구 실행과 승인 상태는 명시적인 단계 이벤트로 기록한다.
- 실행기는 체크포인트 이후부터 멱등하게 재개할 수 있어야 한다.
- LangGraph를 추가해도 사무실 UI와 보고서 데이터 모델은 변경하지 않는다.

## ADR-003: Temporal을 내구성 실행 계층으로 채택한다

상태: 채택  
결정일: 2026-10-04

### 배경

제품은 특정 에이전트 프레임워크보다 범용성과 장기 보수 편의성을 우선한다. 업무는 수초에서 수일까지 지속될 수 있고 사용자 승인, 예약, 외부 이벤트, 재시도, 병렬 처리와 교대 실행이 필요하다. 이 책임을 앱 자체 코드로 계속 구현하면 복구·버전 호환·멱등성 코드가 제품 로직보다 커질 가능성이 높다.

### 결정

Temporal을 업무의 내구성 실행 계층으로 채택한다. 앱의 Workflow Spec은 Temporal과 독립적으로 유지하며 컴파일러가 이를 Temporal Workflow와 Activity 호출로 변환한다.

```text
사무실 UI / 순서도
        ↓
중립 Workflow Spec
        ↓
WorkflowRuntime 인터페이스
        ├─ TemporalRuntime (상용 기본)
        └─ LocalRuntime (개발·마이그레이션)
                ↓
AgentRuntime 인터페이스
        ├─ 직접 모델 API
        ├─ LangGraph
        └─ 기타 에이전트 SDK
                ↓
ToolRuntime / MCP
```

### Temporal을 선택한 이유

- 프로세스나 서버 장애 후 이벤트 기록에서 실행을 복원한다.
- 사용자 승인과 외부 신호를 프로세스를 점유하지 않고 오래 기다릴 수 있다.
- Activity 단위 제한시간, 재시도, 취소와 작업 큐를 제공한다.
- 예약 업무, 교대 근무, 병렬 실행과 하위 워크플로를 일반 업무 기능으로 다룰 수 있다.
- 모델 제공자와 에이전트 프레임워크에 독립적이다.
- 자체 호스팅과 관리형 Cloud 중 선택할 수 있다.

### 비용과 단점

- Temporal Service와 Worker를 운영하거나 Cloud 비용을 부담해야 한다.
- Workflow 코드는 결정적이어야 하며 LLM·DB·네트워크 호출은 Activity로 분리해야 한다.
- 실행 중 Workflow와 새 코드의 호환성을 관리해야 한다.
- 로컬 프로토타입에는 기존 실행기보다 구성과 학습 비용이 크다.

### LangGraph의 위치

LangGraph는 제품 전체의 운영 엔진이 아니라 한 Activity 안에서 복잡한 에이전트 그래프가 필요할 때 사용하는 선택적 AgentRuntime이다. 단순 조사·작성·검수는 직접 모델 어댑터를 사용하고, 동적 분기나 하위 에이전트 탐색이 필요한 업무만 LangGraph를 선택한다.

### 전환 원칙

- API와 UI가 Temporal SDK를 직접 호출하지 않는다.
- PostgreSQL은 제품 데이터의 기준 저장소이고 Temporal은 실행 이력의 기준 저장소다.
- 보고서와 큰 산출물은 PostgreSQL 또는 객체 저장소에 보관하고 Workflow History에는 ID만 둔다.
- 모든 외부 쓰기 Activity는 안정적인 멱등 키를 사용한다.
- 기존 LocalRuntime은 마이그레이션 기간과 단일 PC 개발 모드에서만 유지한다.

## ADR-002: 관계형 영속화와 저장소 경계

상태: 진행 중  
결정일: 2026-10-04

### 결정

단일 `kv.state` JSON 저장을 관계형 컬렉션 테이블로 이전한다. 초기에는 배포가 간단한 SQLite를 유지하되, 스키마 마이그레이션과 트랜잭션을 도입하고 PostgreSQL로 옮길 수 있는 저장소 경계를 만든다.

### 단계

1. SQLite 관계형 테이블과 자동 마이그레이션
2. 기존 `kv.state` 자동 가져오기
3. 업무 실행 체크포인트 및 호출 원장 추가
4. 저장소 인터페이스 분리
5. PostgreSQL 구현과 운영 환경 전환

### 상용 환경의 최종 요구사항

- PostgreSQL 관리형 인스턴스
- 조직·사용자·프로젝트별 tenant ID와 행 수준 격리
- 암호화된 비밀키 저장
- 정기 백업과 시점 복구
- 마이그레이션 롤백 절차
- 연결 풀, 읽기·쓰기 타임아웃과 장애 알림
- 감사 로그 보존 정책
- 개인정보 삭제 및 보존 기간 정책

## ADR-004: 프로젝트 사이트와 라이선스 키로 플랜을 판다

상태: 진행 중 (5단계까지 완료)  
결정일: 2026-10-05

### 배경

앱은 회사마다 자기 PC나 서버에 설치해 쓴다. 그래서 중앙에서 결제해도 고객 앱의 플랜이 저절로 바뀌지 않는다. 동시에 테마·플로우·플레이북을 나누는 커뮤니티와 팀·비즈니스 플랜 판매 창구가 필요하다.

### 결정

- 같은 저장소의 `site/`에 공개 사이트를 둔다. 스택은 앱과 같고(TypeScript·React·Express·PostgreSQL), 포맷 검증 같은 공용 코드는 `shared/`를 함께 쓴다. 운영은 PostgreSQL(Neon 등), 개발과 테스트는 내장 PGlite로 같은 SQL을 쓴다.
- 로그인은 이메일 매직링크·구글·GitHub이고, 검증된 메일 주소로 한 계정에 묶는다.
- 플랜은 **서명된 라이선스 키**로 판다. 사이트가 Ed25519로 서명한 토큰을 발급하고, 앱은 공개키로 검증한다. 앱이 사이트에 묻는 방향(당겨오기)만 써서 공개 주소가 없는 설치에서도 동작하게 한다. 앱 쪽은 기존 `BillingProvider` 구조에 `site` 제공자를 더하고, 갱신은 `billingTick`, 연체 유예는 기존 `GRACE_DAYS`를 그대로 쓴다.
- 결제사는 어댑터 뒤에 두고, 실연동(토스페이먼츠·Paddle 등)은 나중에 고른다. 그 전까지 mock 결제로 전체 흐름을 완성한다.
- 커뮤니티는 테마·플로우·플레이북 갤러리, 크리에이터 프로필·랭킹, 게시판·Q&A, 유료 테마 판매로 단계적으로 연다.

### 사이트에 닿지 못할 때

앱은 결제 기간이 끝나기 3일 전부터 6시간마다 사이트에 새 라이선스를 묻는다. 기간이 지나도록 사이트에 닿지 못하면 결제 실패로 처리하고, 기존 7일 유예가 지나면 개인 플랜으로 돌아간다. 사이트가 라이선스를 거절하면(다른 설치로 옮겨졌거나 삭제됨) 바로 구독을 끝낸다.

### 커뮤니티 항목

- 검증 코드는 앱과 사이트가 같은 것을 쓴다(`server/theme-package.ts`, `shared/flow-pack.ts`, `shared/playbook.ts`). 사이트는 검사를 통과해 정리된 파일만 버전별로 저장하고, 버전은 바꾸지 않는다.
- 업무 흐름은 담당 직원 대신 역할만 담는다. 받는 쪽 사무실에서 같은 역할의 직원(없으면 첫 직원)에게 맞추고, 규칙 검사는 앱의 `validatePlan`을 그대로 쓴다.
- 앱의 원클릭 설치는 앱 서버가 `SITE_URL`에서만, 형식이 맞는 항목 id로만 내려받는다(SSRF 방지). 테마 설치·흐름 저장은 사무실 주인만 한다.

### 운영

- 랭킹은 저장하지 않고 다운로드 일별 집계와 좋아요 시각으로 그때그때 계산한다(좋아요 1 = 다운로드 3). 커지면 일별 스냅샷 테이블로 옮긴다.
- 신고 3명이면 자동으로 가린다. 신고로 가려진 것은 작성자가 다시 공개할 수 없고 운영자만 되돌린다. 운영자 조치는 모두 `audit_log`에 남긴다.
- 정지는 계정 상태 하나로 처리하고 세션을 지운다. 정지된 계정의 항목과 글은 자동으로 지우지 않고 대기열에서 하나씩 처리한다.

### 유료 테마

- 판매는 플랜과 같은 결제 어댑터와 결제 이벤트 처리(중복 이벤트 무시)를 쓴다. 구매 하나는 `purchases` 한 줄이고, 산 사람만 내려받는다.
- 돈의 흐름은 고치지 않는 장부(`ledger`)에 부호 있는 금액으로만 남긴다. 잔액은 합계로 계산하고, 따로 저장하지 않는다. 제작자 70% / 운영 30%.
- 지급은 결제사 정산 기능을 고르기 전까지 운영자가 직접 송금하고 기록한다. 지급 기록은 잔액을 넘지 못하게 계정 행을 잠그고 확인한다.
- 앱의 원클릭 설치는 무료 항목만 한다. 유료 테마는 사이트에서 사고 받은 zip을 앱에 넣는다(기기 로그인 연동은 후속).

### 결제사: Paddle

- 해외(4개 언어) 판매를 위해 판매자 대행(merchant of record)인 Paddle을 고른다. 나라별 부가세와 영수증을 Paddle이 맡고, 한국 판매자도 가입할 수 있다(Stripe는 한국 판매자를 받지 않음).
- 결제 결과는 서명된 웹훅으로만 반영하고, 브라우저는 그 반영을 기다렸다가 돌아간다. 갱신은 Paddle이 청구하고 알리므로 사이트 시계로 갱신하지 않는다.
- 유료 테마(다른 제작자 판매)가 Paddle 정책에 맞는지는 실계정 신청 때 확인하고, 안 되면 유료 테마만 다른 결제 경로로 돌린다.

### 라이선스를 강하게 막지 않는 이유

앱은 AGPL이라 누구나 검증 코드를 고칠 수 있다. 라이선스 키는 정직한 사용자가 결제를 바로 적용하고 갱신하게 돕는 장치로 두고, 복제 방지(DRM)는 하지 않는다. 상업적 재배포는 상업 라이선스로 다룬다.

### 단계

1. 사이트 뼈대: DB·마이그레이션, 로그인 3종, 소개·가격·설치·문서 (완료)
2. 라이선스와 플랜 판매: 서명 키, mock 결제, 발급·갱신·이전, 앱의 `site` 결제 제공자와 플랜 화면 (완료)
3. 커뮤니티 갤러리와 앱 연동(커뮤니티 탭, 원클릭 설치), 플로우 공유 포맷 `avataragent-flow` (완료)
4. 크리에이터 프로필·랭킹, 게시판·Q&A, 검수 (완료)
5. 유료 테마 판매와 정산 장부 (완료)
6. 실결제사 연동과 클라우드 배포 — Paddle 어댑터 완료(샌드박스 시험·배포·실계정 심사 남음)
